# task execution prompt — using embedded default with stack-specific additions
#
# The embedded default handles plan reading, task selection, implementation,
# validation, and commit logic via {{PLAN_FILE}} and {{PROGRESS_FILE}} variables.
# Stack-specific rules below are APPENDED to the embedded logic.
#
# available variables:
#   {{PLAN_FILE}} - path to the plan file being executed
#   {{PROGRESS_FILE}} - path to the progress log file
#   {{GOAL}} - human-readable goal description
#   {{DEFAULT_BRANCH}} - default branch name (main, master, trunk, etc.)

Read the plan file at {{PLAN_FILE}}. Find the FIRST Task section (### Task N: or ### Iteration N:) that has uncompleted checkboxes ([ ]).

NOTE: Progress is logged to {{PROGRESS_FILE}} - this file contains detailed execution steps and can be reviewed for debugging.

CRITICAL CONSTRAINT: Complete ONE Task section per iteration.
A Task section is a "### Task N:" or "### Iteration N:" header with all its checkboxes underneath.
Complete ALL checkboxes in that section, then STOP.
Do NOT continue to the next section - the external loop will call you again for it.

STEP 0 - ANNOUNCE:
Before starting work, output a brief overview (up to 200 words) explaining:
- Which task number you picked and its title
- What the task will accomplish
- Key files or components involved
This helps the user understand what's happening in the current iteration.

STEP 1 - IMPLEMENT:
- Read the plan's Overview and Context sections to understand the work
- Implement ALL items in the current Task section (all [ ] checkboxes under it)
- Write tests for the implementation

STEP 2 - VALIDATE:
- For this project use: yarn lint && yarn typecheck && yarn test:unit
- IMPORTANT: Do NOT use `make` commands for validation — `make` wraps commands in `docker exec` which fails inside the ralphex-dk container. Always use `yarn` directly.
- E2E validation: yarn test:e2e (Playwright auto-starts yarn dev on demand via webServer config — no need for make dev). When debugging specific test failures, run only the affected files first: `yarn test:e2e tests/e2e/specific.spec.ts` — this is much faster than running all tests. Run the full suite only for final validation.
- When E2E tests fail, read the extended trace to understand the failure: check `test-results/<test-name>/error-context.md` for page snapshots and DOM state. Do NOT rely solely on stdout error messages — they often lack context. Look at what the page actually rendered and what network requests were made.
- Fix any failures, repeat until all validation passes

STEP 2.5 - DOC SYNC (after validation passes, before commit):
- Check if the current task modified any of these: zenstack/schema.zmodel, src/app/**/page.tsx, src/app/**/route.ts, src/lib/ module structure, 
- If YES, update the corresponding docs/architecture/*.md Mermaid diagrams inline by reading the changed source files and rewriting the affected diagram sections:
  - schema.zmodel changes → update docs/architecture/erd.md
  - New/changed pages or API routes → update docs/architecture/routes.md
  - New/changed src/lib/ or src/components/ modules → update docs/architecture/modules.md
  - Auth flow changes → update docs/architecture/auth-flow.md
  - New external services or major architecture changes → update docs/architecture/system-overview.md
- If NO relevant files were changed, skip this step

STEP 3 - COMPLETE (after validation passes):
- Update progress: edit {{PLAN_FILE}} and change [ ] to [x] for each checkbox you implemented in the current Task section
- Commit all changes (code + updated plan) with message: feat: <brief task description>
- Push the commit to the remote branch: git push origin HEAD (this creates the remote branch on first push; if push fails due to missing origin remote or auth issues, log a warning but continue)
- Check if any [ ] checkboxes remain in other sections
- If NO more [ ] checkboxes in the entire plan, output exactly: <<<RALPHEX:ALL_TASKS_DONE>>>
- If more sections have [ ] checkboxes, STOP HERE - do not continue

If any phase fails after reasonable fix attempts, output exactly: <<<RALPHEX:TASK_FAILED>>>

REMINDER: ONE section (Task/Iteration) per loop cycle. After commit, STOP and let the loop handle the next section.

OUTPUT FORMAT: No markdown formatting (no **bold**, `code`, # headers). Plain text and - lists are fine. Do not echo phase names or step numbers - just do the work.

## Stack-Specific Rules for T3 Extended SaaS Template

- node_modules are prebuilt in the Docker image. If you see module-not-found or resolution errors (e.g. after package.json changes), run: yarn install --frozen-lockfile
- After ANY change to zenstack/schema.zmodel, run make codegen && make db-migrate BEFORE touching frontend
- Client components: useClientQueries(schema) from @zenstackhq/tanstack-query/react, import schema from @/lib/zenstack/generated/schema-lite (NOT schema.ts)
- Server components: requireSession() -> sessionToDbAuth() -> bindDbAuth() chain is mandatory
- Never edit src/lib/zenstack/generated/ — regenerate instead
- All queries must be scoped by organizationId — no unscoped data access
- TypeScript strict mode: no any, no type assertions without justification
- auth schema (Better Auth) and public schema (app models) are SEPARATE — never cross them
- Unit tests: co-locate as *.test.ts next to the file. E2E tests: tests/e2e/*.spec.ts
- Use Date.now() suffixes for unique test data in E2E tests
- UI components: ALWAYS use shadcn/ui from src/components/ui/ (Button, Card, DataTable, Input, Label, Sonner, Table, Textarea). If a component is missing, install via npx shadcn@latest add <name> — never hand-roll UI primitives
- Forms: React Hook Form + zodResolver + shadcn Input/Label/Button. DataTable for listings. No custom form or table markup
- Every new UI feature MUST have E2E tests that verify it works in a real browser. Capture screenshots with page.screenshot() at key assertion points for visual verification
- E2E tests must assert visible state (text, element visibility, counts) — not just absence of errors
